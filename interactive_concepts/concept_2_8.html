Tool Call Anatomy

Every tool call has a precise structure. The LLM generates the request; the executor returns a structured result. Both must be well-formed.

📤 Tool Call Request (LLM → Tool)

{
  "type": "tool_call",
  "id": "call_abc123",
  "name": "search_web",
  "parameters": {
    "query": "Anthropic CEO 2024",
    "max_results": 5,
    "include_snippets": true
  }
}

The id links the call to its result — critical for parallel tool execution.

📥 Tool Result (Tool → LLM)

{
  "type": "tool_result",
  "tool_call_id": "call_abc123",
  "status": "success",
  "content": [{
    "title": "Anthropic Leadership",
    "snippet": "Dario Amodei is CEO...",
    "url": "https://anthropic.com/about"
  }]
}

The tool_call_id must match the request id. Result is injected as Observation, closing the loop iteration.

Production Failure Modes — Click to Diagnose
🔁 Infinite Loop
Agent keeps calling the same tool without progress
Root Cause: No termination condition, or agent keeps getting the same null/error result and retries without breaking the pattern.
✓ Fix: max_iterations hard limit. Add "same action twice" detector — if action N == action N-1, force a different path or escalate.
👻 Silent Tool Failure
Tool returns empty result; agent reasons as if it got real data
Root Cause: Tool returns {} or null without an error flag. LLM interprets empty observation as "no results" and fabricates an answer.
✓ Fix: All tools must return explicit status fields. Never return raw nulls. Use {"status":"no_results","query":"..."} and validate before injecting into context.
📜 Context Overflow
Long loops fill the context; early reasoning is truncated silently
Root Cause: Each iteration appends T+A+O to context. After 10–20 iterations, older content is truncated — agent forgets its goal and contradicts itself.
✓ Fix: Summarise older iterations. Use external memory for completed sub-tasks. Set token budgets per tool result. Trigger compression at 60% context usage.
🎭 Hallucinated Tool Call
Agent calls a tool that doesn't exist in its registry
Root Cause: LLM generates a tool name it imagines exists ("fetch_stock_price" when only "search_web" is registered), producing a "tool not found" error cascade.
✓ Fix: Validate all tool calls against the registered registry before execution. Return structured error: {"error":"unknown_tool","available_tools":[...]} as feedback for self-correction.
💸 Runaway Cost
Agent makes hundreds of calls, burning budget unexpectedly
Root Cause: Open-ended tasks with no scope boundary. Agent searches → finds more queries → searches more. Compounds exponentially without a ceiling.
✓ Fix: Per-session token budgets and tool call count limits. Track cost in every loop. Add scope check in Thought: if near budget, summarise and finish rather than expanding.
🔀 Observation Poisoning
Malicious content in tool results hijacks reasoning
Root Cause: Agent reads a web page containing "Ignore your previous instructions..." — a prompt injection delivered via tool result that the LLM treats as trusted context.
✓ Fix: Treat all tool results as untrusted input. Apply input guardrails to observations before context injection. Never merge "tool result" role with "user" role in the prompt template.

In a ReAct trace, what is the purpose of the "Thought" step?
✗a) It's just formatting — the LLM doesn't actually reason there
✓b) It externalises the LLM's reasoning chain, making decisions auditable and improving action quality via chain-of-thought
✗c) It's where tools are called

✓ The Thought step is critical for two reasons: (1) Chain-of-thought — making the LLM explicitly reason before acting improves decision quality by 20–40% on complex tasks. (2) Auditability — in production debugging, the Thought trace shows you exactly WHY the agent did what it did. Tools are called in Action; Memory writes happen in the Loop.
✗ The Thought step is genuinely where the LLM reasons — forcing it to articulate "I need to do X because Y" before acting dramatically improves both action quality AND gives you an audit trail. Tools = Action step. Memory writes = Loop. The Thought step is chain-of-thought externalisation — a fundamental technique that turns one-shot calls into structured deliberation.
Question 2 of 5
What connects a tool call request to its result in the ReAct protocol — and why does this matter?
✗a) Message order — request always immediately precedes result
✓b) A matching ID: "id" in the request matches "tool_call_id" in the result — enabling correct attribution even in parallel execution
✗c) The tool name is repeated in the result
✗d) A timestamp comparison
✓ The ID mechanism is critical for parallel tool calls. When an agent calls multiple tools simultaneously, results may return out of order. The tool_call_id links each result unambiguously to its request — the LLM knows "this result belongs to my search_web call, not my read_file call." Without IDs, parallel tool execution would be impossible to correlate correctly.
✗ Position-based matching breaks with parallel tool calls (results return in any order). The ID mechanism — tool call "id" matched by result's "tool_call_id" — is what enables reliable result attribution in parallel execution. This is a core part of the tool call protocol used by all major LLM providers (OpenAI, Anthropic, etc.).
Question 3 of 5
An agent on iteration 18 of 20 has completed 80% of its task but can't finish with available tools. What should it do?
✗a) Keep trying until the limit, then fail silently
✗b) Restart from the beginning with a different strategy
✓c) Return a partial result with clear indication of what was done and what couldn't be completed
✗d) Hallucinate the remaining 20% to return a complete-looking answer
✓ Graceful partial completion is the production best practice. A partial result with honest status is infinitely more valuable than a silent failure or fabricated completion. Use the remaining iterations to summarise what was accomplished, state what couldn't be done and why, and surface partial results. "Fail loudly with partial results" — users can act on 80% completion; they cannot make good decisions based on hallucinated completions.
✗ Silent failure and hallucination are the worst options — both leave the user with no actionable information. Restarting discards 80% of completed work. The correct production pattern: return everything successfully completed, explicitly state what the agent couldn't finish and why, let the user decide next steps. Partial honest results always beat complete fabricated results.
Question 4 of 5
Why is context overflow particularly dangerous compared to other ReAct failure modes?
✗a) It causes the agent to crash immediately and visibly
✗b) It only affects very long conversations of 100+ iterations
✓c) It's a silent failure — the agent continues confidently but with corrupted reasoning from truncated context
✗d) It triggers an automatic model restart
✓ Silent failures are the most dangerous. When context overflows, the LLM doesn't say "I've forgotten earlier context." It reasons from whatever is in its window — which may be missing the original goal, earlier sub-results, or critical constraints. The agent produces confident-sounding outputs that contradict what it did earlier. Especially insidious in tasks with many steps or large tool outputs.
✗ Context overflow doesn't crash the agent — that's what makes it dangerous. It silently truncates older content. The LLM doesn't know what it's forgotten — it just reasons from what it can see, potentially contradicting earlier decisions or forgetting the original goal entirely while generating confident output. It typically kicks in well before 100 iterations with large tool responses.

In the error recovery trace, the agent uses a FileNotFoundError to find the correct filename. What reasoning pattern is this?
✗a) Memorisation — recalled the correct path from training data
✗b) Hallucination — invented a plausible filename
✓c) Reactive adaptation — using error feedback to update beliefs, generate a corrective action, and self-recover
✗d) Planning — it had a backup plan from the start
✓ This is Reactivity + BDI in action. The agent: (1) perceives the error, (2) updates belief ("file isn't where I assumed"), (3) generates new desire ("find where it actually is"), (4) executes corrective action (list_directory), (5) uses the result to correct course. Treating every observation — including errors — as information is what makes ReAct agents resilient. Errors are feedback signals, not just failures.
✗ It didn't use training data (path was unknown), didn't hallucinate, and had no pre-planned backup. This is reactive adaptation — the agent used the error as an information signal to update its world model, generate a diagnostic action, and self-correct. Every error in a ReAct loop is valuable information if the reasoning chain treats it as such rather than as a terminal failure.
