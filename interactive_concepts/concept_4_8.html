The Three ReWOO Modules
🧠
Planner
Uses the LLM to analyze the query and produce a structured plan — a DAG of tool calls with variable references (#E1, #E2…). Called once at the start.
LLM-Powered
⚙️
Worker
Pure execution layer — no LLM needed. Runs each tool call from the plan, respects dependencies, can execute independent steps in parallel.
Tool-Execution Only
🎯
Solver
Receives a compact evidence bundle (just the results, no tool-call history). Uses LLM to synthesize the final answer — clean, minimal context.

ReWOO vs ReAct — Detailed Comparison
DimensionReActReWOO
LLM calls per taskN calls (one per thought+action)2 calls (Planner + Solver)
Token usageGrows with each step — all history in contextCompact — evidence dict only in Solver
Parallelism❌ Sequential by design✅ Worker steps can run in parallel
AdaptabilityHigh — reacts to observations in real-timeLow — plan is fixed upfront
Best forDynamic tasks, uncertain tool resultsStructured research, data aggregation
CostHigh — repeated LLM calls with growing contextLow — ~60% cheaper on average
LatencySequential bottleneckLower — parallel worker execution
Failure recoveryGood — can observe errors and retryPoor — plan must be re-generated
When to Use ReWOO
✅ Use ReWOO When…
Task requires multiple searches / tool calls that you can enumerate upfront
Tool results are predictable (e.g., web search, DB queries)
Cost and latency are primary concerns
Steps are mostly independent (parallelizable)
Research, data aggregation, report generation tasks
❌ Avoid ReWOO When…
Task outcome depends on intermediate results (deep conditional logic)
Tools can fail and require dynamic recovery
Plan cannot be determined without observing early steps
Creative/generative tasks with unknown shape
Tools have unpredictable output formats
