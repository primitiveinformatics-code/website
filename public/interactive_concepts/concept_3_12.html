RAG Foundations: Why RAG?

The four knowledge problems that LLMs cannot solve alone — and why Retrieval-Augmented Generation is the standard answer.

The Core Idea
RAG in one sentence: Instead of asking the model to know everything, give it a search engine — retrieve relevant documents at query time, inject them into the context window, then generate a response grounded in those documents.

The formula: RAG = Retrieval (find relevant docs) + Augmentation (add to prompt) + Generation (LLM answers from them) 
# The RAG pattern — simplified
def rag_query(user_question: str) -> str:
    # 1. RETRIEVE — find relevant chunks from your knowledge base
    relevant_docs = vector_db.search(
        query=user_question, top_k=5
    )

    # 2. AUGMENT — inject retrieved docs into the prompt
    augmented_prompt = f"""
    Context from knowledge base:
    {chr(10).join(doc.text for doc in relevant_docs)}

    User question: {user_question}
    Answer based only on the above context.
    """

    # 3. GENERATE — LLM answers from retrieved context
    return llm.call(augmented_prompt)
4 Knowledge Problems RAG Solves

Click each problem to see how RAG addresses it.

📅

1. Knowledge Cutoff

LLMs have a training cutoff date. They cannot answer questions about events after their last training run — no matter how you ask.

temporal staleness
🏢

2. Private / Proprietary Data

Your company's internal docs, Confluence pages, Jira tickets, and product specs were never in the training set. The model simply doesn't know them.

domain gap
🔍

3. Grounding & Citations

Without source documents, the model cannot cite where an answer came from. You can't audit hallucinations or verify accuracy.

traceability
💾

4. Context Window Limits

You can't stuff an entire knowledge base into the context window. A 100k-document corpus at 500 tokens each = 50M tokens — far beyond any model's limit.

scale

RAG vs Fine-Tuning vs In-Context Learning
Dimension RAG Fine-Tuning In-Context Learning
Knowledge update Real-time — update the vector DB, not the model Hours–days to retrain and redeploy Instant — just change the prompt
Knowledge scale Unlimited — billions of docs in vector DB Limited by training data size / cost Context window only (e.g., ~200K tokens)
Traceability High — can return source chunks with answer None — knowledge baked into weights opaquely Full — you put the docs there yourself
Cost Medium — embedding + vector DB + inference High — GPU hours for each training run Low — just inference (but bigger context = more tokens)
Best for Dynamic knowledge bases, internal docs, product search Teaching new skills or style, domain-specific tasks requiring deep adaptation A small known set of examples, few-shot prompting, fixed reference docs
Hallucination risk Lower — answer is grounded in retrieved text Medium — model generalizes from training Medium — depends on quality of in-context docs

How RAG Works: The 5 Steps
This is the high-level flow. The next concept (3.13) dives deep into each of the two pipelines — Indexing and Retrieval.
1

Ingest & Chunk

Source documents (PDFs, wikis, Confluence, code) are split into overlapping chunks — typically 256–512 tokens each. Overlap ensures context isn't lost at chunk boundaries.

2

Embed

Each chunk is passed through an embedding model (e.g., text-embedding-3-small, nomic-embed) to produce a dense vector that captures semantic meaning.

3

Store in Vector DB

Vectors are stored in a vector database (Pinecone, Weaviate, pgvector, Chroma). The original text is stored as metadata alongside each vector.

4

Query-Time Retrieval

The user's question is embedded with the same model, then compared against all stored vectors using cosine similarity (or ANN search). The top-k most similar chunks are returned.

5

Augmented Generation

Retrieved chunks are injected into the LLM prompt as context. The model generates an answer grounded in those specific passages, with citations available for traceability.
