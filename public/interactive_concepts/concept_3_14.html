Session 3 · Concept 3.14

Chunking Strategies

How you split documents determines what your RAG system can find. The wrong chunking strategy silently destroys retrieval quality.

Why Chunking Is the Most Underestimated Step
The core tension: Small chunks → high retrieval precision (you find the exact passage), but low context per chunk (the LLM doesn't have enough to answer). Large chunks → rich context per chunk, but retrieval imprecision (you retrieve a whole section when you needed one sentence). Chunking strategy is about resolving this tension for your specific document type.

Strategy Deep Dives

Fixed-Size (Recursive Character) Chunking

Split text at a target token count, trying natural separators first: paragraph breaks → sentence breaks → word breaks → characters. The chunk_overlap slides a window so that boundary context is preserved in both adjacent chunks.
Implementation
from langchain.text_splitter import \
    RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,
    chunk_overlap=64,
    separators=[
        "\n\n",  # paragraph break
        "\n",    # line break
        ". ",    # sentence end
        " ",     # word break
        ""       # character (last resort)
    ]
)
chunks = splitter.split_documents(docs)

Pros

  • Simple to implement
  • Predictable chunk sizes
  • Good default baseline
  • Works on any text

Cons

  • Splits mid-sentence sometimes
  • Ignores document structure
  • Overlap tuning is manual
📌 Use when: You need a quick, reliable baseline and don't have time to tune. Works well for general prose.

Sentence-Level Chunking

Split on sentence boundaries using an NLP sentence tokenizer (spaCy, NLTK). Each chunk is 1–3 sentences. Maximizes retrieval precision for Q&A — you retrieve the exact sentence that answers the question, not a surrounding paragraph.
Implementation (spaCy)
import spacy
nlp = spacy.load("en_core_web_sm")

def sentence_chunks(text, window=2):
    doc = nlp(text)
    sents = list(doc.sents)
    chunks = []
    for i in range(0, len(sents), window):
        group = sents[i:i+window]
        chunks.append(
            " ".join(s.text for s in group)
        )
    return chunks

Pros

  • Highest retrieval precision
  • Respects semantic units
  • Great for FAQ-style docs

Cons

  • Very small chunks = low LLM context
  • Needs NLP library
  • Cross-sentence context lost
📌 Use when: Your documents are FAQ-style, highly dense, and questions map to individual sentences. Pair with parent-child for better context.

Semantic Chunking

Embed every sentence, then detect "meaning breaks" where cosine similarity between adjacent sentences drops sharply. Chunk at those semantic boundary points. Produces variable-size chunks that are each thematically coherent.
Implementation (LlamaIndex)
from llama_index.node_parser import \
    SemanticSplitterNodeParser
from llama_index.embeddings.openai import \
    OpenAIEmbedding

splitter = SemanticSplitterNodeParser(
    buffer_size=1,
    # Split when similarity drops below
    # this percentile threshold
    breakpoint_percentile_threshold=95,
    embed_model=OpenAIEmbedding()
)
nodes = splitter.get_nodes_from_documents(docs)

Pros

  • Thematically coherent chunks
  • Best for dense technical docs
  • No fixed size limits

Cons

  • Slowest — embeds every sentence
  • Needs embedding model at index time
  • Threshold requires tuning
📌 Use when: Documents have dense multi-topic sections (e.g., medical papers, legal contracts). Worth the extra cost for complex corpora.

Parent-Child (Small-to-Big) Chunking

Store two levels: small child chunks (128 tokens) for high-precision retrieval, and large parent chunks (1024 tokens) for rich LLM context. Retrieve using child vectors, but inject the parent chunk into the prompt. Best of both worlds.
Implementation (LangChain)
from langchain.retrievers import \
    ParentDocumentRetriever
from langchain.text_splitter import \
    RecursiveCharacterTextSplitter

# Small chunks → used for retrieval
child_splitter = RecursiveCharacterTextSplitter(
    chunk_size=200
)
# Large chunks → returned to LLM
parent_splitter = RecursiveCharacterTextSplitter(
    chunk_size=2000
)

retriever = ParentDocumentRetriever(
    vectorstore=vector_db,
    docstore=doc_store,
    child_splitter=child_splitter,
    parent_splitter=parent_splitter
)

Pros

  • High precision + high context
  • Works great for long-form docs
  • No information loss at retrieval

Cons

  • More complex setup
  • Needs separate docstore
  • 2x storage overhead
📌 Use when: Long documents (books, reports, manuals) where you need precise retrieval but the LLM needs surrounding context. The go-to production pattern.

Document-Aware (Structure-Based) Chunking

Split on semantic document structure: Markdown headers, HTML tags, code block boundaries, PDF section headings. Each chunk maps to a meaningful unit of the document — a section, a function, a table — preserving its natural context.
Markdown-Aware Splitting
from langchain.text_splitter import \
    MarkdownHeaderTextSplitter

headers_to_split = [
    ("#", "H1"),
    ("##", "H2"),
    ("###", "H3"),
]
splitter = MarkdownHeaderTextSplitter(
    headers_to_split_on=headers_to_split
)
# Each chunk gets section metadata:
# {"H1": "Installation", "H2": "Config"}
chunks = splitter.split_text(markdown_text)

Pros

  • Preserves document intent
  • Section metadata enables filtering
  • Great for technical docs & wikis

Cons

  • Requires consistent doc structure
  • Very long sections need secondary split
  • Format-specific parsers needed
📌 Use when: Your corpus is well-structured (Confluence, GitHub wikis, API docs). Metadata from headers dramatically improves filter-based retrieval.
