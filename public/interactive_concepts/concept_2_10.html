All 5 Patterns — Click to Explore
🔄
Single ReAct Agent
One model, one loop, one context

The simplest and most common pattern. One LLM runs a Think→Act→Observe loop with a set of tools. Best for focused tasks that fit within a single context window.

  • Task complexity is moderate and well-defined
  • Expected to complete in 5–15 iterations
  • No need for specialised sub-agents
  • Debugging simplicity is a priority
  • Examples: research Q&A, email drafting, data lookup
🗂️
Planner–Executor
Separate planning from execution

A Planner LLM decomposes the task into a structured plan; one or more Executor agents carry out individual sub-tasks. The Planner monitors progress and adapts as results come in.

  • Task has multiple discrete, sequential sub-tasks
  • Different sub-tasks need different tool sets
  • Plan may need to adapt based on intermediate results
  • Examples: software project planning, market research reports
⚡
Parallel Fan-Out
Multiple agents working simultaneously

A coordinator spawns multiple identical or specialised agents that work in parallel on independent sub-tasks. Results are aggregated when all agents complete. Dramatically reduces wall-clock time.

  • Task decomposes into truly independent sub-tasks
  • Latency reduction is a key requirement
  • Sub-tasks don't share state or depend on each other
  • Examples: crawling 20 competitors simultaneously, parallel data processing
🔍
Critic (Evaluator–Optimizer)
Generator + Critic in a quality loop

A Generator agent produces candidate outputs; a Critic agent evaluates them against criteria and provides structured feedback. The loop runs until quality criteria are met or max iterations reached.

  • Output quality is highly variable and hard to predict
  • Clear quality criteria can be defined
  • Iterative refinement is acceptable
  • Examples: code generation + test runner, essay writing + fact-checker, translation + backtranslation
🌐
Hierarchical Multi-Agent
Orchestrator → Specialised sub-agents

An Orchestrator manages a network of specialised agents, each expert in a domain. The Orchestrator delegates tasks, aggregates results, resolves conflicts, and maintains global state across the system.

  • Task spans multiple domains requiring specialised expertise
  • Scale requires distributed execution
  • Sub-agents may themselves use tools or spawn sub-agents
  • Examples: enterprise automation, full-stack dev agent, multi-domain research platform

Question 1 of 5
You need to write and test a Python function. The LLM generates code and your test suite validates it. Which pattern fits?
✗a) Parallel Fan-Out
✗b) Hierarchical Multi-Agent
✓c) Critic (Evaluator–Optimizer)
✗d) Single ReAct Agent
✓ The Critic/Evaluator-Optimizer pattern is a perfect fit. Generator (LLM) produces code → Critic (test suite) evaluates it and returns structured failure messages → Generator revises → loop continues. The test suite IS the symbolic verifier in a neuro-symbolic hybrid. This is exactly how AlphaCode and GitHub Copilot's test-driven generation works.
✗ This is a Generate → Evaluate → Refine loop with clear quality criteria (tests pass/fail). That's the Critic pattern. Parallel Fan-Out is for independent parallel tasks. Hierarchical MAS is for multi-domain complexity. Single ReAct could work for simple code but lacks the structured quality-feedback loop. The test suite acting as a critic is what makes this Evaluator-Optimizer.
Question 2 of 5
You need to analyse 50 competitor websites simultaneously to build a market map. Which pattern minimises wall-clock time?
✗a) Single ReAct Agent — one agent visits all 50 sequentially
✗b) Planner–Executor — plan then execute one site at a time
✓c) Parallel Fan-Out — spawn 50 agents simultaneously, aggregate results
✗d) Critic pattern — generate summaries and evaluate them
✓ Parallel Fan-Out cuts the wall-clock time from 50× to ~1× (bounded by the slowest agent). Since each competitor analysis is independent — no competitor's data affects another's — there are no ordering dependencies. A coordinator spawns 50 agents, each analyses one site, all results stream back in parallel, coordinator aggregates. This is the canonical fan-out use case.
✗ Sequential patterns (Single ReAct, Planner-Executor) take 50× as long. The Critic pattern is for iterative quality refinement. When tasks are fully independent (no cross-dependencies), Parallel Fan-Out is the pattern. Spawn 50 concurrent agents → each handles one competitor → aggregate when all complete. Wall-clock time drops to the latency of the SLOWEST single agent, not the sum of all 50.
Question 3 of 5
What is the MAIN risk of using Hierarchical Multi-Agent for a simple task that could be done by one agent?
✗a) The task will fail because multi-agent systems can't handle simple tasks
✓b) Unnecessary orchestration overhead: higher cost, latency, and debugging complexity with no quality benefit
✗c) Hierarchical systems have a maximum of 3 sub-agents
✗d) The Orchestrator will always produce incorrect results for simple tasks
✓ Over-engineering is a real and expensive problem. For a task like "summarise this document," using a hierarchical MAS means: Orchestrator → Planner sub-agent → Executor sub-agent → Critic sub-agent → result. Each hop burns tokens and adds latency. The same result comes from one ReAct loop in 1 iteration. Architectural complexity should always be proportionate to task complexity.
✗ Hierarchical MAS can handle simple tasks just fine — it will just do it expensively. The risk is unnecessary overhead: 4–6 LLM calls instead of 1, orchestration messages, coordination latency, and 3 times the debugging surface. The right pattern for a simple task is a Single ReAct Agent. Pattern selection should always match the task's actual complexity — not default to the most sophisticated architecture.
Question 4 of 5
In the Planner–Executor pattern, why does the Planner need to monitor intermediate results (not just plan once upfront)?
✗a) To log each step for audit purposes
✗b) Because the Executor cannot be trusted to work independently
✓c) Because intermediate results may reveal that the original plan is unachievable or needs replanning
✗d) To count the number of tokens used
✓ This is the BDI principle applied to multi-agent systems: Beliefs must be updated as the world changes. A plan made at T=0 may be obsolete at T=5 if an Executor discovers that a data source is unavailable, an API returned unexpected results, or a sub-task took 10x longer than expected. Adaptive planning — where the Planner revises the remaining plan based on what Executors actually found — is what separates robust production systems from brittle sequential pipelines.
✗ Audit logging and token counting don't require the Planner to monitor results. Executor independence isn't the issue. The core reason is adaptive planning: the world doesn't behave as expected. If sub-task 3 discovers that the data source assumed in steps 4–7 doesn't exist, the Planner needs to replan steps 4–7. A Planner that only plans once upfront is just a sequential script — it's the adaptive replanning that makes it an agent system.
Question 5 of 5
Which two patterns are BEST combined when you need both parallel execution AND quality verification of the aggregated result?
✗a) Single ReAct + Planner–Executor
✓b) Parallel Fan-Out + Critic
✗c) Hierarchical + Single ReAct
✗d) Planner–Executor + Parallel Fan-Out
✓ The Fan-Out + Critic combination is a powerful production pattern. Phase 1: Fan-Out spawns N parallel agents to gather/process data quickly. Phase 2: Aggregator combines the parallel results. Phase 3: Critic evaluates the aggregate for consistency, factual accuracy, and completeness — triggering regeneration of specific sections if needed. This is used in production research systems, competitive intelligence pipelines, and multi-source news synthesis agents.
✗ Think about what each phase needs. "Parallel execution" = Fan-Out (spawn N concurrent agents). "Quality verification of aggregated result" = Critic (evaluate + refine). These two combine naturally: Fan-Out collects data fast → Aggregator merges → Critic validates the synthesis → Generator revises weak sections. This two-phase pattern (gather fast, verify carefully) is a cornerstone of production research and intelligence pipelines.
