Query Rewriting
Transform the user's raw query into retrieval-optimised forms before hitting the index
Pre-Retrieval
The Problem
User queries are conversational and ambiguous. "What about the pricing?" is meaningless to a vector search without conversation context.
Techniques
Step-back prompting: abstract to general principle. Multi-query: generate 3–5 query variations. HyDE: generate hypothetical answer (see card 3). Query decomposition: split complex queries.
Example Rewrite
Original: "What about the pricing?"
Rewritten: "What is the pricing model and cost structure for [product] based on our conversation context?"
When to Apply
Multi-turn conversations. Queries with pronouns. Complex multi-hop questions. Vague or ambiguous user intent.
Pipeline
Raw Query → LLM Rewrite → 3–5 Queries → Parallel Retrieve → Deduplicate & Merge
Recall boost over raw query retrieval
+30–45%

Cross-Encoder Re-Ranking
Re-score the top-K candidates with a more powerful relevance model before sending to LLM
Post-Retrieval
The Problem
Bi-encoder embeddings (dense retrieval) retrieve by semantic similarity but can miss nuanced relevance. A chunk about "ML training" might score highly for "how do I train my dog" — same semantic space.
How It Works
Retrieve top-50 candidates cheaply (bi-encoder). Then pass each (query, chunk) pair to a cross-encoder that scores joint relevance. Re-rank by cross-encoder score. Send top-5 to LLM.
Bi-encoder vs Cross-encoder
Bi-encoder: embed independently, fast (ANN search). Cross-encoder: jointly processes query+doc, 10–100× slower but much more accurate. Use both in sequence (coarse-to-fine).
Tools
Cohere Rerank API, BGE Reranker, ms-marco-MiniLM, FlashRank (local, free). Most cost <$0.001 per 100 docs.
Coarse-to-Fine Pipeline
Query → ANN Search (top-50) → Cross-Encoder (top-50) → Re-ranked top-5 → LLM
Precision boost (NDCG@5) vs bi-encoder only
+25–35%

HyDE — Hypothetical Document Embedding
Generate a hypothetical answer first — then use that answer as the query embedding
Query Transformation
The Key Insight
The embedding space of a question is different from the embedding space of an answer. Documents in the index look like answers. Embedding a hypothetical answer bridges this gap.
How It Works
1. User asks Q. 2. LLM generates a plausible (but possibly hallucinated) answer. 3. Embed the hypothetical answer. 4. Search the index with this answer-shaped embedding. 5. Real docs cluster near hypothetical answer.
When It Shines
Questions where the answer vocabulary differs from the query vocabulary. Complex technical questions. Queries that produce short documents but the answer is in a long paragraph.
Trade-off
✅ +40–60% recall on complex questions
⚠️ Extra LLM call (cost + latency). Hallucinated hypothesis can lead retrieval astray for factual questions.
HyDE Flow
Q: "How does X work?" → LLM: generate hypothetical answer → Embed(hypothetical) → Retrieve real docs
Recall improvement on knowledge-intensive QA
+40–60%
04
🌳
RAPTOR — Recursive Abstraction
Build a tree of cluster summaries — retrieve from any level, matching query abstraction level
Indexing Architecture
The Problem It Solves
Chunked RAG retrieves isolated fragments. For "summarise the main themes of this 100-page report", no single chunk has the answer. Need document-level and section-level summaries, not just chunk-level.
How RAPTOR Works
1. Chunk documents. 2. Cluster similar chunks (UMAP + GMM). 3. Summarise each cluster → higher-level nodes. 4. Repeat recursively → tree. 5. Index ALL levels. 6. At query time, retrieve from the most appropriate level.
Multi-Level Retrieval
High abstraction query (themes, summary) → retrieves from top-level cluster summaries.
Specific query (exact detail) → retrieves from leaf-level chunks.
Routing is automatic via embedding similarity.
Trade-off
✅ Handles multi-granularity queries. Best for large, complex documents.
⚠️ Expensive to build index (clustering + LLM summarization per level). 3–5× indexing cost.
RAPTOR Tree Structure
Whole-doc summary (root) ↓ Cluster summaries ↓ Section summaries ↓ Raw chunks (leaves)
Improvement on multi-document summarisation tasks
+40–55%
