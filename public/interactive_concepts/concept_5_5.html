Why Agent Security Is a New Problem

Traditional web apps can be patched with firewalls and input sanitisation. Agents can be attacked through natural language, through retrieved data, and through the tools they trust — attack surfaces that didn't exist before.

Traditional Security vs Agent Security

🔒 Traditional Web App Security

Attack EntryExplicit: HTTP params, form fields, API inputs
Attack TypeSQL injection, XSS, CSRF — well-understood, patchable
Trust ModelCode doesn't change. Known logic = predictable behaviour
Sanitise?Yes — WAFs, input validators, prepared statements work well
ActionsApp executes predefined operations — no autonomous decisions
Blast RadiusScoped to application boundary

🤖 Agentic System Security

Attack EntryAny text the agent reads: user input, documents, web pages, emails
Attack TypePrompt injection, jailbreaks, data poisoning, tool hijacking
Trust ModelLLM follows natural language — an attacker speaks the same language as the app
Sanitise?No reliable sanitisation — you can't regex-filter an LLM's mind
ActionsAgent takes autonomous actions: send emails, delete records, call APIs
Blast RadiusAll tools the agent has access to — potentially org-wide

Key Insights
The attacker speaks the same language as your app. Any text the agent reads is a potential attack vector — including retrieved documents, email subjects, and web page content. Traditional input sanitisation is ineffective.
Principle of Least Privilege is your strongest defence. An agent that can only read (not write) can't be tricked into deleting data. Scope tool permissions to the minimum required for each task.
Indirect prompt injection is the most dangerous. The user didn't write the attack — a malicious document or web page did. Your users are innocent; your retrieval pipeline is the vulnerability.
Irreversibility is the real threat multiplier. A confused agent that sends one wrong email is a nuisance. An agent with delete-all database access is catastrophic. Always audit action reversibility before granting tool access.
