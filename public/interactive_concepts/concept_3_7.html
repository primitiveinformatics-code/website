Transport Layers

HTTP+SSE, WebSockets, and stdio — the three transports that carry MCP and A2A messages, and exactly when to use each one.

Local Process

How It Works

  • Client POSTs requests to /message endpoint
  • Client GETs /sse endpoint — server keeps connection open
  • Server pushes events as data: {...}\n\n lines
  • Standard HTTP — works through proxies, CDNs, firewalls
  • Each request is independent HTTP round-trip

Strengths

  • Works everywhere — no special firewall rules needed
  • Horizontally scalable with load balancers
  • Built-in HTTP auth (Bearer, API keys)
  • Reconnects automatically on disconnect
  • Compatible with all HTTP frameworks

Limitations

  • Half-duplex — server pushes, client polls via POST
  • Higher overhead per message (HTTP headers)
  • Some proxies buffer SSE — tune Nginx/Caddy timeouts
  • Not ideal for very high-frequency messages (>100/sec)

Best For

  • Remote MCP servers (cloud-hosted tools)
  • A2A agent communication across organizations
  • Shared team tool servers behind HTTP auth
  • Production deployments with existing CDN/proxy

How It Works

  • Single TCP connection upgraded from HTTP via Upgrade: websocket
  • Full-duplex — both sides send at any time
  • Framed binary or text messages, low overhead
  • Connection persists until explicitly closed
  • Subprotocols can layer MCP/A2A JSON on top

Strengths

  • True bidirectional — server can push without a pending GET
  • Lower per-message overhead than HTTP+SSE
  • Better for real-time, high-frequency interactions
  • Single connection = lower connection overhead

Limitations

  • Some corporate proxies and firewalls block WebSockets
  • Harder to load-balance (sticky sessions needed)
  • Reconnection logic must be implemented manually
  • Not yet the primary MCP/A2A standard transport

Best For

  • High-frequency streaming (chat UIs, real-time agents)
  • Controlled internal deployments (not crossing firewalls)
  • Agent-to-agent communication on same internal network
  • Low-latency interactive applications

How It Works

  • Client spawns the MCP server as a child process
  • JSON messages written to server's stdin
  • Responses read from server's stdout
  • Errors routed to stderr
  • Newline-delimited JSON — one JSON object per line

Strengths

  • Zero network stack — maximum speed for local tools
  • No ports, no firewall rules, no auth overhead
  • Process lifecycle managed by OS — auto-cleanup
  • Simple to implement — just read/write streams
  • Perfect for CLI tools, IDE plugins, desktop agents

Limitations

  • Local only — cannot be accessed over a network
  • One client per server process
  • Server restarts when client disconnects
  • No built-in auth (process-level trust assumed)

Best For

  • Local MCP servers (filesystem, git, shell, DB)
  • IDE integrations (Cursor, VS Code, Windsurf)
  • Developer machines — local agent tooling
  • Single-user desktop AI applications
