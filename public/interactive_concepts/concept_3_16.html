Vector Databases

The storage and search layer behind every RAG system. How ANN indexing works, which DB to pick, and when pgvector is enough.

Why Regular Databases Can't Do This
The problem: A regular SQL query like WHERE text LIKE '%password reset%' is keyword matching — it misses "how do I recover my account" entirely. A vector DB finds documents whose meaning is close to the query, regardless of exact word overlap. This requires a fundamentally different data structure: an Approximate Nearest Neighbor (ANN) index. 
# SQL: keyword match — misses semantic variants
SELECT * FROM docs WHERE text LIKE '%password reset%'
# MISSES: "recover account", "forgot credentials", "change login"

# Vector DB: semantic similarity — finds all related passages
results = vector_db.query(
    vector=embed("how do I reset my password"),
    top_k=5
)
# FINDS: "change password", "recover account", "forgot credentials"

Major Vector Databases

Pinecone

Fully ManagedHybrid Search

Strengths

  • Zero infrastructure to manage
  • Auto-scaling, always available
  • Namespaces for multi-tenant isolation
  • Hybrid dense+sparse search (serverless)
  • Metadata filtering with full query API

Limitations

  • Vendor lock-in
  • Higher cost at scale vs self-hosted
  • Data leaves your infrastructure
  • Less control over index tuning
# Upsert + query with metadata filter
index.upsert(vectors=[("id1", embedding, {"doc_type": "policy", "date": "2024-03"})])
results = index.query(vector=q_vec, top_k=10, filter={"doc_type": "policy"})

Qdrant

Self-HostedCloud Available

Strengths

  • Best-in-class hybrid search (dense+sparse)
  • Rich payload filtering
  • HNSW with full configurability
  • Open-source, data stays on-prem
  • Built-in quantization for memory savings

Limitations

  • Requires self-hosting expertise
  • Scaling requires ops knowledge
  • Smaller ecosystem than Pinecone
# Hybrid search: dense + BM25 sparse
from qdrant_client.models import Query, Prefetch, FusionQuery
results = client.query_points(collection_name="docs", prefetch=[
  Prefetch(query=dense_vec, using="dense", limit=20),
  Prefetch(query=sparse_vec, using="sparse", limit=20),
], query=FusionQuery(fusion="rrf"), limit=5)

Weaviate

Self-HostedCloud Available

Strengths

  • GraphQL + REST API — powerful querying
  • Built-in hybrid BM25+dense
  • Schema with relationships between objects
  • Native multimodal (text + image)

Limitations

  • Schema definition required upfront
  • Higher memory usage vs alternatives
  • Steeper learning curve
# Hybrid search via Python client
results = client.collections.get("Documents").query.hybrid(
  query="password reset", alpha=0.75, # 0=BM25, 1=dense
  limit=5
)

pgvector

PostgreSQL Extension

Strengths

  • Runs inside existing PostgreSQL DB
  • Full SQL: JOINs, transactions, ACID
  • No new infra if you already use Postgres
  • HNSW index available (v0.5+)

Limitations

  • Slower than dedicated vector DBs at scale
  • 10M+ vectors needs careful tuning
  • No built-in hybrid search
# pgvector: vector similarity inside SQL
CREATE TABLE docs (id bigserial PRIMARY KEY, content text, embedding vector(1536));
CREATE INDEX ON docs USING hnsw (embedding vector_cosine_ops);
SELECT content, embedding <=> $1 AS distance
FROM docs ORDER BY distance LIMIT 5;

Chroma

Open SourceLocal-First

Strengths

  • Dead simple Python API
  • Zero config for local development
  • In-memory or persistent modes
  • Great for prototyping and notebooks

Limitations

  • Not designed for production scale
  • No hybrid search
  • Limited filtering capabilities
  • Performance degrades past ~100K docs
# Chroma: prototype in 5 lines
import chromadb; client = chromadb.Client()
col = client.create_collection("docs")
col.add(documents=["..."], ids=["doc1"])
results = col.query(query_texts=["my question"], n_results=5)
