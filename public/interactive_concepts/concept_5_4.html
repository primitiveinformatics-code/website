Knowledge-Practice Gap — Agent Evaluation

Teams know evaluation matters. In practice, 78% of production agents have no structured evaluation pipeline. Explore why the gap exists and the 4 strategies to close it.

The Knowledge-Practice Gap

📚 What Teams Know

✓ Agents can hallucinate at any step
✓ Technical success ≠ goal achievement
✓ Evaluation must be continuous, not one-off
✓ Need semantic metrics beyond HTTP status
✓ Evaluation should run in CI/CD pipeline

Widely understood in the community. Docs, papers, and frameworks all emphasize evaluation.

⟹
GAP

⚠️ What Teams Do

✗ Manual spot-checks, not systematic evals
✗ No eval suite in CI — ships without testing
✗ Latency measured, semantic quality ignored
✗ Find failures from user complaints, not monitoring
✗ No ground truth dataset — "it works in the demo"

78% of production agents have no structured evaluation pipeline. (Source: Multiple industry surveys 2024–25)

The 4 Evaluation Strategies
🔬
Offline Evaluation
Pre-deployment evaluation against a curated test set
Offline evaluation runs your agent against a dataset of (input, expected_output) pairs before deploying to production. It's the agentic equivalent of unit + integration tests. Build a ground-truth dataset from real user sessions, annotated by domain experts. Run it in CI on every code change.

✅ Strengths

  • Catches regressions before users see them
  • Fully deterministic, repeatable
  • Cheap — no live traffic needed
  • Can run in CI/CD pipeline

⚠️ Limitations

  • Dataset must be maintained and kept current
  • Doesn't capture real user distribution
  • Only tests known failure modes
  • Dataset creation requires expert effort
Example Code — DeepEval
from deepeval import evaluate from deepeval.metrics import AnswerRelevancyMetric, FaithfulnessMetric from deepeval.test_case import LLMTestCase test_cases = [ LLMTestCase( input="What is Priya's renewal date?", actual_output=agent.run("What is Priya's renewal date?"), expected_output="September 1, 2026", retrieval_context=[customer_context] ) ] evaluate(test_cases, metrics=[AnswerRelevancyMetric(), FaithfulnessMetric()])
🤖
LLM-as-Judge
Use a more capable LLM to evaluate your agent's outputs
Deploy a secondary LLM (often GPT-4o or Claude Opus) as a judge. The judge receives a rubric, the original task, and the agent's output — and scores quality dimensions like accuracy, helpfulness, safety, and task completion. Highly scalable: can score millions of responses asynchronously.

✅ Strengths

  • Scalable — scores all production traffic
  • Flexible rubrics for any task type
  • Catches nuanced quality issues
  • Provides explanation, not just a score

⚠️ Limitations

  • Judge itself can be wrong or biased
  • Adds latency and cost to the pipeline
  • Positional bias — judge prefers first answer
  • Requires careful rubric engineering

🔁
Online Shadow Evaluation
Run a challenger agent in parallel on live traffic — compare without user impact
Shadow evaluation routes a copy of real production traffic to a new agent version without serving its responses to users. Compare the two versions across semantic metrics. When the challenger consistently outperforms, promote it. Enables risk-free A/B testing of agent changes at scale.

✅ Strengths

  • Uses real user query distribution
  • No user impact — shadow responses discarded
  • Reveals real-world regressions before rollout
  • Enables continuous improvement loops

⚠️ Limitations

  • 2× inference cost during shadow phase
  • Write-action agents can't be shadowed safely
  • Complex infrastructure to route + compare
  • Still needs semantic scoring for comparison
Shadow Eval Architecture
# Traffic Router async def handle_request(query): # Serve production agent prod_response = await prod_agent.run(query) # Shadow: run challenger, discard response challenger_response = await challenger_agent.run(query) # Async eval comparison (doesn't block user) asyncio.create_task( evaluator.compare(prod_response, challenger_response, query) ) return prod_response # Only prod response shown to user
🧪
Human-in-the-Loop Evaluation
Domain experts annotate a sample of agent outputs — the gold standard
Automated metrics measure proxy signals. Human evaluation measures what actually matters: did a domain expert consider this output correct, safe, and helpful? Run human eval on a stratified sample of production traffic. Use it to calibrate automated judges and surface systematic failures that metrics miss.

✅ Strengths

  • Ground truth — highest signal quality
  • Catches failures automated metrics miss
  • Calibrates and validates your LLM judges
  • Required for high-stakes domains (legal, medical)

⚠️ Limitations

  • Expensive and slow — can't scale to all traffic
  • Annotator agreement can be low (<70%) on subjective tasks
  • Latency: days/weeks, not real-time
  • Requires domain expertise — can't outsource easily

Key Insights
The gap is not knowledge — it's activation energy. Teams know evaluation matters but face friction: no dataset, no tooling, no owner. Solve the infrastructure and ownership problem first.
Start with offline evals on 10 golden test cases before building anything more sophisticated. 10 well-chosen cases catch 80% of regressions. Perfect is the enemy of good here.
LLM-as-judge is not ground truth. It's a scalable proxy. Always calibrate your judge against human annotations quarterly. A judge that diverges from human judgment is worse than no judge.
Evaluation is a product, not a project. It needs an owner, a roadmap, and ongoing maintenance — just like the agent itself. Teams that treat eval as a one-time setup always regress.
